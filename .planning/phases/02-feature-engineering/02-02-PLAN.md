Leakage assertion contract (this plan implements it):
  1. Reload dados/matches_train.parquet AND dados/matches_test.parquet and concat.
  2. Build a minimal long-format team-match table with just (id, date, season, team, goals_scored).
     Do NOT call build_features here — the point is to reconstruct the rolling step
     independently so a bug in build_features does not silently invalidate the leakage check.
  3. Compute the RAW rolling output (no imputation) via
     groupby(['team','season']).transform with
     lambda x: x.shift(1).rolling(5, min_periods=5).mean()
  4. For each (team, season) group, the FIRST match (by sorted [date, id]) MUST have NaN
     in the raw rolling output. Using groupby(['team','season']).apply(lambda x: x.iloc[0], include_groups=False),
     count how many of the first rows are NaN. The count of NaN values must equal the
     total number of (team, season) groups.
  5. Print: Leakage check PASSED: nan_count/total_groups first-match rows are NaN as expected.

  This assertion catches the worst class of feature-engineering bugs:
    - rolling(5).shift(1) instead of shift(1).rolling(5) (current match leaks in)
    - min_periods=1 instead of min_periods=5 (early-season rows get pseudo-valid values)
    - Forgetting to groupby season (window crosses season boundaries)
  Any of these mistakes would leave non-NaN values in first-of-season rows.
